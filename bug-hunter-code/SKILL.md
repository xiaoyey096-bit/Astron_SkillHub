# 代码缺陷定位与质量审查助手（bug-hunter-code）

> 中文技能名：**代码审查助手**
> 定位：把「一段代码」变成「一份分级的审查报告」——缺陷、安全、规范三维度，每条问题给位置、风险、修复建议和可直接抄的修复示例。静态规则扫描 + AI 语义判断双轨，不联网、不调外部模型、不执行用户代码。

本文件是 AI 调用入口。当用户触发以下任一场景时应加载本 Skill，并按下面的标准工作流程（SOP）执行。

> **能力边界（重要）**：本 Skill 只做**对用户已提供的代码文本进行静态审查与建议**。**不具备**：联网拉取仓库代码、对接 CI/CD、执行/运行用户代码做动态测试、自动提交修复 PR、做性能基准测试。

---

## 一、核心原则（不可违反）

1. **静态规则交给脚本，语义判断交给 AI**：可模式化的缺陷与安全规则（`shell=True`、`eval`、`SELECT` 拼接、`sk-` 密钥、`os.system` 等）由 `scripts/review.py` 扫描得到**确定性结论**；语义级问题（逻辑错误、命名是否恰当、异常处理是否合理）由 AI 基于上下文判断并标注「建议复核」。
2. **不执行用户代码**：全程静态分析，绝不 import/exec/运行用户提供的代码（有安全风险且不可复现）。所有结论来自文本扫描与语义阅读。
3. **每条问题可执行**：报告里每条必须含「位置（文件:行或代码片段）+ 问题 + 风险等级 + 修复建议 + 修复示例代码」，不能只说"这里有风险"。
4. **不夸大不漏报**：规则命中按规则定义如实报；语义判断标注不确定性，不把"可能"说成"一定"。低风险的风格问题不与高危安全漏洞混为一谈。
5. **修复示例必须正确**：给出的修复代码要语法正确、确实解决问题，不能引入新 bug。

## 二、何时加载本 Skill（触发与边界）

当用户请求命中下面**任一**场景时加载：

| 场景关键词 | 对应维度 |
|-----------|---------|
| "审查/review/检查/有没有问题"一段代码 | 全维度（缺陷+安全+规范） |
| "安全吗/漏洞/注入/有没有安全隐患" | 安全维度为主 |
| "规范吗/坏味道/可读性/命名" | 规范维度为主 |
| "找出 bug/缺陷/会崩溃吗" | 缺陷维度为主 |

**不应加载**的情况（避免跨场景误触发）：
- 用户要"帮我写/补全一段新代码" → 本 Skill **不做代码生成**，只审查已有代码；
- 用户要"运行/跑一下这段代码看结果" → 本 Skill **不执行代码**；
- 用户要"帮我做性能压测/基准测试" → 本 Skill **不做动态性能测试**，仅能给静态性能提示。

## 三、标准工作流程（SOP）

### 第 1 步：接收代码并识别语言

**输入形式**（任一）：
- 代码文件路径：`.py`/`.js`/`.ts`/`.java`/`.go`/`.rs`/`.c`/`.cpp` 等；
- 粘贴的代码文本（带或不带语言标注）。

**识别动作**：
1. 按扩展名或代码特征识别语言（Python/JS/TS/Java/Go/...）。识别不出则询问。
2. 统计代码规模（行数、函数/类数），超长（>500 行）提示分段审查。
3. 调用脚本：`python scripts/review.py scan <文件路径> --lang <语言>`（语言可省，脚本自动猜）。

### 第 2 步：三维度扫描

#### 维度 A：缺陷与潜在 Bug（脚本规则 + AI 语义）
脚本扫描确定性缺陷模式（见 `references/defect-rules.md`），如：
- 资源未释放（打开文件/连接未 close、未用 with/try-finally）；
- 可能的空值/未初始化使用；
- 异常被空 `except` 吞掉；
- 循环中低效操作（如在循环里打开文件/查询数据库）。

AI 补充语义级缺陷：逻辑错误、边界条件遗漏、返回值未处理等，标「建议复核」。

#### 维度 B：安全漏洞（脚本规则为主，高危优先）
脚本扫描安全规则（见 `references/security-rules.md`），覆盖：
- 命令注入（`shell=True`/`os.system`/`exec`/`subprocess` 拼接用户输入）；
- SQL 注入（字符串拼接 SQL 而非参数化）；
- 硬编码密钥（`sk-`/`password=`/`api_key=` 真值）；
- 路径穿越（用户输入直拼路径、ZIP 解压无 zip-slip 防护）；
- 不安全反序列化（`pickle.loads`/`eval` 处理外部数据）；
- SSL 验证禁用（`verify=False`/`CERT_NONE`）。

AI 补充上下文相关安全判断（如某输入是否真来自用户、是否可信源）。

#### 维度 C：规范与坏味道（脚本统计 + AI 语义）
脚本统计：函数圈复杂度（粗略，按分支关键字计数）、超长函数（>50 行）、重复代码块（简单行重复检测）。
AI 补充：命名规范、魔法数字、注释缺失、异常处理是否合理。

### 第 3 步：分级与去重

所有发现按风险分级：
- 🔴 **严重**：安全漏洞（注入/密钥/反序列化）、会导致崩溃或数据损坏的缺陷；
- 🟡 **警告**：潜在缺陷（资源泄漏、异常吞没）、明显规范问题；
- 🟢 **建议**：风格、可读性、轻微优化。

**去重**：同一位置同类问题合并为一条；脚本与 AI 都报的以脚本结论为准、AI 补充语义说明。

### 第 4 步：输出审查报告

按 `templates/review-report-template.md` 输出，结构固定：
1. 审查总览（语言、规模、各等级问题数）；
2. 问题清单（按 🔴🟡🟢 分组，每条含位置/问题/风险/修复建议/修复示例）；
3. 整体评价（代码质量概览、最该优先修的 Top 问题）；
4. 局限说明（静态分析覆盖范围、未做的动态检查）。

默认在对话区呈现 Markdown。用户要求导出时输出经 sanitize 的 CSV（问题清单）。

- **输入**：代码文件路径或粘贴代码文本。

## 五、异常与边界情况处理清单（鲁棒性保障）

| 异常情况 | 处理方式 |
|---------|---------|
| 代码为空 / 仅注释 | 报告"无可执行代码"，不强行审查 |
| 语言识别不出 | 询问语言；默认按通用规则扫安全关键词 |
| 代码超长（>500 行） | 提示分段上传或聚焦某函数/模块 |
| 脚本未命中任何规则 | 不编造问题，报告"未发现模式化缺陷"，AI 仍做语义通读并给整体评价 |
| 代码片段不完整（缺上下文） | 对能判的判，需上下文的标「需更多上下文确认」 |
| 用户给的是配置文件（YAML/JSON） | 转入安全配置审查（硬编码密钥、SSL 禁用等），不做代码逻辑审查 |
| 用户要求"运行验证修复" | 告知不执行代码，建议用户自行运行测试 |
| 用户要求"帮我重写整个文件" | 告知不做大规模重写，仅给针对性修复示例 |
| 框架/库特定 API 难判 | 标「建议复核」，不武断下结论 |
| 代码含特殊字符 | sanitize_cell 净化表格字段 |
| 误报争议 | 每条附判定依据，用户可据此复核；脚本规则类给出规则名 |

## 六、结果验收标准

- 对 `samples/vulnerable_demo.py`（含命令注入、SQL 拼接、硬编码密钥、空 except、资源未释放等已知问题）执行全流程，应：
  1. 检出 ≥4 类安全问题且至少 1 条 🔴严重；
  2. 每条问题含位置、风险等级、修复建议、修复示例；
  3. 修复示例语法正确、确实消除原问题；
  4. 给出整体评价与优先修复 Top。
- 对 `samples/clean_demo.py`（合规代码）应报告"未发现严重问题"，不编造。

测试命令：`python tests/run_test.py`。

## 七、不应该做什么（边界与合规）

1. **不执行用户代码**：绝不 import/exec/运行用户提供的代码，全程静态分析。
2. **不联网**：不拉取仓库、不查 CVE 库在线接口、不调外部模型，规则库本地内置。
3. **不编造问题**：规则未命中、语义无明显问题的，不凑数；报告"未发现"是合理结论。
4. **不做大规模重写**：只给针对性修复示例，不替用户重写整个文件。
5. **不漏报高危**：安全漏洞类规则必须扫全，即使代码量大。
6. **修复示例不负责任**：给出的修复代码必须语法正确、确实解决问题，不引入新风险。
